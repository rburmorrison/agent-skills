# Personal Engineering Guidance

Complete planning before editing. Ask as many consequential questions as needed, one at a time, allowing each answer to inform the next. Explain options and recommendations; obtain agreement on decisions affecting behavior, scope, public contracts, data ownership, I/O boundaries, and architecture before implementation. Do not treat silence or general permission to implement as agreement to a new choice. Scale planning to the change; a small, unambiguous correction needs only a brief plan.

Use `plan-changes` to prepare an implementation-ready plan with exact boundary contracts, concrete steps and expected verification outcomes, a documentation change map, and explicit remaining discretion. Continue from an agreed plan when one exists, including after a model switch in the same chat. Preserve decisions, their reasons, and supporting user answers or established requirements. Do not infer the future implementing model's capabilities.

Use `code-authoring` to carry out an agreed change. Choose local implementation details autonomously within its boundaries. Keep optional improvements outside the change unless included in the agreed scope.

Alongside tests, exercise the changed application as a user would through its actual CLI, UI, API, or caller when feasible. Use authorized, disposable inputs and inspect visible results and relevant state. If execution is unavailable, use the closest feasible check and clearly report what remains unverified; passing tests do not establish that an unexecuted workflow works.

Prefer meaningful domain names, explicit data contracts, cohesive functions and modules, and concentrated I/O boundaries. In functions with more than one logical step, introduce each meaningful stage with a short, imperative comment, including stages inside loops or branches. Explain consequential decisions near the relevant code. Separate conceptual units with whitespace, and put a blank line above each comment group unless it starts its enclosing block. Straightforward single-step predicates and mappings usually need no comments; compact match arms form one unit. Apply the same readability standard to tests while allowing their failure-on-error shortcuts. Use `code-authoring` for the detailed standard and examples.

Use `setup-project` when establishing a new project. Establish strict tooling appropriate to its language and supported versions. Manage dependencies through the project's package manager rather than guessing versions and editing dependency entries by hand.

Lint suppressions must be rare, narrowly scoped, and accompanied by a specific reason. Explain configuration-level exceptions beside the setting. Fix underlying issues when possible; do not weaken checks merely to obtain a passing result.

For non-trivial changes, use a separate reviewer agent with fresh context and the `review-changes` skill. Fix validated findings within scope and rerun affected checks. Default to one full review; request targeted follow-ups autonomously when fixes warrant them.

If implementation reveals a missing consequential choice or requires changing agreed behavior, scope, or the documentation map, explain the issue and ask the user immediately. Pause dependent work, continue independent work, and record the answer and rationale before resuming. Do not reopen settled choices without new evidence, invent behavior, or silently narrow acceptance criteria. Clearly identify work that remains incomplete while awaiting an answer or capability.

Keep the final handoff concise. Explain what changed and why, then use a factual numbered list describing the entry point, its trigger, and the important parts of the code flow. Include roles, inputs and outputs, effects, and design reasons where they help understanding. Give every named code location a clickable local file link with an absolute path and verified line number. Use short descriptive labels rather than directions to read or review code. Summarize important tested behavior, actual workflow results, and verification limitations in a separate closing paragraph. Follow `code-authoring`'s handoff guidance for the format and scale the detail to the change.

Apply `code-authoring`'s documentation standards, including during fixes and skill maintenance. Useful inline implementation comments and source API doc comments/docstrings are allowed for affected code. READMEs, guides, standalone reference material, help, and user examples may be edited only at locations and for corrections or additions explicitly stated in the plan. By default, plan only accuracy fixes; new documents or previously undocumented facts require an explicit user request or confirmation, even inside an existing passage. The planner may propose an addition but must obtain confirmation before including it. Leave accurate content unchanged. At the end of a change, inspect related existing documentation; if an unplanned edit is needed, ask for a plan amendment before touching it. Follow documentation lints, surface requirements outside the permitted scope, and use Title Case for authored headings.

These conventions are defaults. Follow explicit task-specific instructions that override them, retain unaffected defaults, and record the overrides in the plan so they survive model changes. An explicitly requested review cadence replaces the default cadence rather than adding another mandatory review.

These defaults support the current request and applicable project conventions. They do not authorize additional scope, commits, publishing, installation, or external actions. If a named skill or required reviewer capability is unavailable, state the limitation rather than claiming it was used.
